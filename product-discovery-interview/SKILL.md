# 产品需求访谈与澄清

目标是在开始较大规模实现前，把“我大概想做什么”转化为可讨论、可取舍、可验收的产品定义。重点不是生成一份看起来完整的 PRD，而是主动发现用户尚未考虑的问题、隐藏假设、冲突约束和失败场景，并把真正影响开发的决策关闭到足够安全的程度。

默认使用用户语言；专业术语可保留英文。不要为了形式感把用户拖进冗长问卷，也不要因为有了一个大致想法就立即开始编码。

## 何时使用

适合：

- 新产品、新子系统、新工作流或明显改变用户体验的功能；
- 用户有理想形态，但需求仍不完整、边界不清或存在较多隐含决策；
- 需求同时涉及交互、数据、权限、兼容性、发布或迁移；
- 用户明确要求“多问一些问题”“先帮我想清楚再开发”。

不适合：

- 已经有明确复现步骤和验收标准的 bug 修复；
- 小范围文案、样式、重命名或机械性修改；
- 用户明确要求先做一次性原型，且已经接受暂时忽略未决问题。

如果任务介于两者之间，使用轻量模式，只确认真正会改变方案的少量问题。

## 核心原则

1. **先查已有事实，再问用户。** 仓库、现有产品、文档和可验证环境已经能回答的问题，不重复让用户回答。
2. **先理解目标，再讨论功能。** 先确认为什么做、给谁用、什么结果算成功，再进入页面和实现细节。
3. **问题分轮提出。** 每轮优先 3–7 个高价值问题，按主题归组；根据回答继续追问，不一次抛出几十道问题。
4. **区分事实、假设和决策。** 不把模型推断、行业惯例或竞品做法冒充用户已确认需求。
5. **主动暴露取舍。** 发现多个合理方案时，说明收益、成本、风险与推荐，不要求用户从无上下文的选项中盲选。
6. **关键未知项未关闭前，不进入重实现。** 可以做调研、原型或验证性实验，但不得把临时假设固化为正式需求。
7. **保持比例感。** 产品发现服务于开发，不制造与风险不成比例的文档负担。

## 工作流程

### 1. 盘点已有上下文

先读取当前仓库中与产品相关的 README、docs、issues、设计稿、已有页面、配置、测试和当前行为。已有项目优先理解现状，不让用户重复已经明确的信息。

先给出一个短的“当前理解”，至少包括：

- 产品/功能的目标；
- 主要使用者；
- 已知输入、输出和核心流程；
- 已确认约束；
- 当前仍可能影响设计的未知项。

对现有产品做改造时，再补一项：**哪些现有行为必须保持兼容**。

### 2. 必要时做轻量外部校验

只有当外部事实会显著影响产品决策时，才做有限的现状校验，例如：平台能力、主流交互范式、直接替代方案、协议/标准、竞品已经验证过的明显约束。目标是避免在错误前提上提问，不是产出独立研究报告。

- 优先一手来源和当前可验证事实；
- 只收集足以影响本次决策的信息；
- 明确区分“外部事实”“观察到的行业做法”“我们的产品选择”；
- 找不到可靠证据时标为未知，不用模糊印象代替。

### 3. 第一轮：确认产品目标

优先问会改变产品方向的问题，例如：

- 谁是主要用户，谁不是；
- 用户当前如何完成这件事，最大痛点是什么；
- 最关键的 1–3 个使用场景；
- 成功标准是什么，哪些行为或结果能证明产品有效；
- 这是个人工具、内部工具、公开产品还是可扩展平台；
- 哪些能力必须第一版就有，哪些可以延后。

不要把“你想要什么功能”作为唯一问题。

每轮问题结束后，先用几句话复述新增结论与仍未解决的点，再进入下一轮；不要让用户连续回答多轮，却看不到需求如何逐步收敛。

### 4. 第二轮：补齐使用流程与边界

根据第一轮回答，只检查与当前产品相关的维度：

- **用户流程**：入口、核心步骤、完成状态、返回/撤销/重试；
- **信息与数据**：数据来源、结构、生命周期、导入导出、版本兼容；
- **状态**：空状态、加载、处理中、成功、失败、部分成功；
- **异常**：网络失败、权限不足、损坏输入、重复操作、并发冲突；
- **权限与角色**：谁能看、创建、编辑、删除、分享；
- **兼容性**：旧数据、旧配置、平台差异、迁移方案；
- **可恢复性**：失败后能否继续、是否需要自动保存或历史版本；
- **非功能要求**：性能、离线、可访问性、隐私、安全、可维护性；
- **生命周期**：首次使用、日常使用、升级、停用、删除。

不要机械遍历清单。某一维度不会改变当前方案时，直接跳过。

### 5. 第三轮：明确交互与产品决策

当功能边界稳定后，再确认用户真正会看到和操作的行为：

- 页面/视图和导航关系；
- 用户每一步能执行的主要动作；
- 默认值和自动化程度；
- 何时需要确认、警告或阻止操作；
- 用户是否能理解当前状态和下一步；
- 哪些信息必须突出，哪些应隐藏到高级设置；
- 是否需要批量操作、搜索、筛选、撤销、历史记录或快捷键。

遇到交互取舍时给出推荐，并说明为什么这个选择更符合前面确认的目标。

## 问题与决策账本

访谈过程中维护一个简短账本，不要求单独建文件，但最终规格中要能看出这些状态：

- `Q-xx`：未解决问题；标明 `blocking` 或 `non-blocking`；
- `D-xx`：已经确定的产品决策；注明是用户确认还是暂定默认；
- `A-xx`：暂时接受但尚未验证的假设；注明验证方式或风险；
- `AC-xx`：可观察、可验证的验收标准。

规则：

- `blocking` 问题没有关闭时，不应把相关实现写成已确定范围；
- 暂定默认必须显式暴露，不能伪装成用户决定；
- 同一个决定不要在多个位置用不同措辞重复维护；
- 重要产品决定发生变化时，同步检查受影响的 `AC`。

## 收敛范围

将需求整理为四类：

- **Must**：没有它第一版就不能解决核心问题；
- **Should**：价值高，但可以在核心闭环之后完成；
- **Could**：有益但不影响首版成立；
- **Out of scope**：本轮明确不做。

范围项应尽量关联到用户场景和验收标准，而不是只列功能名。

## 形成可开发规格

在仓库已有文档规范时遵循现有位置；否则可以建议写入 `docs/product/PRODUCT_SPEC.md`，但不要仅为了使用本 Skill 强制创建文件。

规格至少包含：

- 背景与目标；
- 目标用户与主要场景；
- 核心用户流程；
- Must / Should / Could / Out of scope；
- 关键交互与状态；
- 数据与兼容性要求；
- 异常与恢复策略；
- 非功能要求；
- `D-xx` 关键决策；
- `AC-xx` 验收标准；
- `Q-xx` 未决问题和 `A-xx` 暂定假设。

验收标准描述可观察行为，例如：

`AC-04：导入损坏文件时显示可理解的错误，已有数据保持不变，用户可以重新选择文件。`

不要写“错误处理完善”这类无法判定完成的句子。

## 进入开发的门槛

满足以下条件后，才建议进入正式实现：

- 核心用户和核心问题明确；
- 首版范围已收敛；
- 主流程和关键异常流程已定义；
- 会显著改变架构、数据格式或用户合同的决策已确认；
- Must 范围有足够的 `AC-xx` 判断是否完成；
- 不存在会使主要实现方向失效的 `blocking Q-xx`；
- 剩余未知项不会迫使大量已完成代码推倒重来。

如果仍有高风险未知项，优先做小型技术验证或交互原型，并把验证结果带回需求阶段。

## 向执行阶段交接

需要交给长程 Agent 时，`agent-goal-brief` 应直接读取本阶段产出的 `D/A/Q/AC`，不要重新向用户询问已经明确的产品决策。

交接时至少说明：

- 哪些 `AC-xx` 属于本次实现；
- 哪些 `D-xx` 是不可擅自改变的产品决定；
- 哪些 `A-xx` 可以通过实现验证；
- 哪些 `Q-xx` 仍未关闭，执行 Agent 遇到时必须停下或绕过，不得自行把它变成产品决定。

## 与其他 Skill 的配合

推荐链路：

`product-discovery-interview` → `agent-goal-brief` → 实现与验证 → `product-documentation` / `product-demo-visuals` → `project-closeout`

- 产品目标明确且需要自主长程执行：交给 `agent-goal-brief`。
- 产品已经实现，需要写用户文档：使用 `product-documentation`。
- 需要真实运行产品并制作高质量截图：使用 `product-demo-visuals`。
- 开发和交付完成后统一对齐现役事实：使用 `project-closeout`。

小任务不要机械串完整链路。

## 交付说明

结束访谈时明确告诉用户：已经确认了什么、仍有哪些 `blocking/non-blocking` 未决问题、哪些是假设、首版建议范围是什么、哪些 `AC` 定义了完成，以及是否已经达到可以安全开发的程度。不要把未确认内容伪装成最终产品决定。
