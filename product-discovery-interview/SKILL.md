# 产品需求访谈与澄清

目标是在开始较大规模实现前，把“我大概想做什么”转化为可讨论、可取舍、可验收的产品定义。重点不是生成一份看起来完整的 PRD，而是主动发现用户尚未考虑的问题、隐藏假设、冲突约束和失败场景。

默认使用用户语言；专业术语可保留英文。不要为了形式感把用户拖进冗长问卷，也不要因为有了一个大致想法就立即开始编码。

## 何时使用

适合：

- 新产品、新子系统、新工作流或明显改变用户体验的功能；
- 用户有理想形态，但需求仍然不完整、边界不清或存在较多隐含决策；
- 需求同时涉及交互、数据、权限、兼容性、发布或迁移；
- 用户明确要求“多问一些问题”“先帮我想清楚再开发”。

不适合：

- 已经有明确复现步骤和验收标准的 bug 修复；
- 小范围文案、样式、重命名或机械性修改；
- 用户明确要求先做一次性原型，且已经接受暂时忽略未决问题。

如果任务介于两者之间，使用轻量模式，只确认真正会改变方案的少量问题。

## 核心原则

1. **先理解目标，再讨论功能。** 先确认为什么做、给谁用、什么结果算成功，再进入页面和实现细节。
2. **问题分轮提出。** 每轮优先 3–7 个高价值问题，按主题归组；根据回答继续追问，不一次抛出几十道问题。
3. **区分事实、假设和决策。** 不把模型推断或行业惯例冒充用户已确认需求。
4. **主动暴露取舍。** 发现多个合理方案时，说明收益、成本、风险与推荐，不要求用户自己从无上下文的选项中盲选。
5. **关键未知项未关闭前，不进入重实现。** 可以做调研、原型或验证性实验，但不得把临时假设固化为正式需求。
6. **保持比例感。** 产品发现服务于开发，而不是制造文档负担。

## 工作流程

### 1. 盘点已有上下文

先读取当前仓库中与产品相关的 README、docs、issues、设计稿、已有页面、配置和测试。已有项目优先理解当前行为，不让用户重复已经明确的信息。

输出一个短的当前理解，至少包括：

- 产品/功能的目标；
- 主要使用者；
- 已知输入、输出和核心流程；
- 已确认约束；
- 当前仍可能影响设计的未知项。

### 2. 第一轮：确认产品目标

优先问会改变产品方向的问题，例如：

- 谁是主要用户，谁不是；
- 用户当前如何完成这件事，最大痛点是什么；
- 最关键的 1–3 个使用场景；
- 成功标准是什么，哪些指标或行为能证明产品有效；
- 这是个人工具、内部工具、公开产品还是可扩展平台；
- 哪些能力必须第一版就有，哪些可以延后。

不要把“你想要什么功能”作为唯一问题。

### 3. 第二轮：补齐使用流程与边界

根据第一轮回答，检查至少这些维度中与任务相关的部分：

- **用户流程**：入口、核心步骤、完成状态、返回/撤销/重试；
- **信息与数据**：数据来源、结构、生命周期、导入导出、版本兼容；
- **状态**：空状态、加载、处理中、成功、失败、部分成功；
- **异常**：网络失败、权限不足、损坏输入、重复操作、并发冲突；
- **权限与角色**：谁能看、创建、编辑、删除、分享；
- **兼容性**：旧数据、旧配置、平台差异、迁移方案；
- **可恢复性**：失败后能否继续、是否需要自动保存或历史版本；
- **非功能要求**：性能、离线、可访问性、隐私、安全、可维护性；
- **生命周期**：首次使用、日常使用、升级、停用、删除。

只追问与当前产品相关的项，不机械遍历清单。

### 4. 第三轮：明确交互与产品决策

当功能边界已经稳定，再确认用户真正会看到和操作的产品行为：

- 页面/视图和导航关系；
- 用户每一步能执行的主要动作；
- 默认值和自动化程度；
- 何时需要确认、警告或阻止操作；
- 用户是否能理解当前状态和下一步；
- 哪些信息必须突出，哪些应隐藏到高级设置；
- 是否需要批量操作、搜索、筛选、撤销、历史记录或快捷键。

遇到交互取舍时给出推荐，并说明理由。

### 5. 收敛范围

将需求整理为四类：

- **Must**：没有它第一版就不能解决核心问题；
- **Should**：价值高，但可以在核心闭环之后完成；
- **Could**：有益但不影响首版成立；
- **Out of scope**：本轮明确不做。

同时建立一个简短的决策记录：`问题 / 结论 / 理由 / 是否已确认`。

### 6. 形成可开发规格

在仓库已有文档规范时遵循现有位置；否则建议写入 `docs/product/PRODUCT_SPEC.md`，但不要仅为了使用本 Skill 强制创建文件。

规格应至少包含：

- 背景与目标；
- 目标用户与主要场景；
- 核心用户流程；
- Must / Should / Could / Out of scope；
- 关键交互与状态；
- 数据与兼容性要求；
- 异常与恢复策略；
- 非功能要求；
- 明确的验收标准；
- 未决问题和暂定假设。

验收标准应描述可观察行为，例如“导入损坏文件时显示可理解的错误并保持已有数据不变”，而不是“错误处理完善”。

## 进入开发的门槛

满足以下条件后，才建议进入正式实现：

- 核心用户和核心问题明确；
- 首版范围已收敛；
- 主流程和关键异常流程已定义；
- 会显著改变架构或数据格式的决策已确认；
- 验收标准足以判断功能是否完成；
- 剩余未知项不会迫使已完成的大量代码推倒重来。

如果仍有高风险未知项，优先做小型技术验证或交互原型，并把验证结果带回需求阶段。

## 与其他 Skill 的配合

- 需求确定后，需要规划和编写产品文档时，使用 `product-documentation`。
- 需要真实运行产品并制作高质量截图时，使用 `product-demo-visuals`。
- 这三个 Skill 可以串联，但不要对一个很小的任务机械执行完整链路。

## 交付说明

结束本轮访谈时，应明确告诉用户：已经确认了什么、仍有哪些未决问题、哪些是假设、首版建议范围是什么，以及是否已经达到可以安全开发的程度。不要把未确认内容伪装成最终产品决定。
