# GitHub 交付

## 仓库边界

- 先检查交付目录的 Git 根目录、状态、分支、远端和现有修改。用户提供仓库则复用；既有仓库正在维护时不另建替代仓库。
- 用户要求新建但未指定名称/可见性时，可从课程名取唯一可读名称并默认 private，交付时说明。发现同名仓库先核对用途，不能覆盖陌生仓库。
- 沿用已有目录约定，不将当前 cwd 的所有内容自动纳入。提交前查看暂存文件，排除个人作业、用户附件、提取缓存、虚拟环境、编辑器状态、Token 与本地绝对路径。版权与来源说明随资料保留；仓库可见性不替代原文件使用权限。
- 检查托管平台的实际文件限制。遇到超限材料先完成笔记和来源清单，再采用平台支持且符合用户意图的存储方式；不要反复推送已知会失败的大文件或偷偷删除资料来声称完整交付。

## 工具与同步

优先使用当前可用且足以执行操作的 GitHub 连接器；本地大批量 Git 操作用 Git/gh CLI 更直接时可用 CLI。凭证交由连接器或既有凭据管理器，不写入文件。工具不可用时先完成本地交付，再明确连接/权限阻碍。

1. 核对远端最新状态；有并发变更先检查差异并安全集成，不默认 force push、重置或丢弃本地工作。
2. 结构与必要内容测试通过后，暂存确定的交付文件并检查差异；提交信息围绕最终改动。
3. 按用户既有要求推送。仓库没有分支策略时，小型个人笔记库可直接提交当前主分支；现有仓库使用 PR 时遵循约定。创建 PR 后若环境提供附件工具，将 PR 关联到当前任务。
4. 读取远端分支 SHA，确认与预期提交一致。`origin/main` 是本地跟踪引用，需 fetch/远端查询后才可当作远端证据。
5. 若有 CI，查看本次 SHA 的运行，而非仅看绿色徽章或上一轮结果。等待采取有界、适当间隔的方式；CI 失败就读日志、修复并重跑；遇到相同外部服务故障且没有新线索时停止盲目重试，报告剩余问题。

## 轻量 CI

已有工作流则扩展；用户要求可持续维护或整套仓库建设时可添加。工作流运行与本地相同的检查，按实际课程数量校验，不写死示例课程的讲数或资源数。

如使用本 skill 的脚本：复制到 `tools/verify_pack.py`，仓库根目录运行 `python3 tools/verify_pack.py .`；内容数值测试独立运行。脚本仅依赖 Python 标准库。选取当时受支持的 runner、Python 和 Actions 版本，避免照搬历史版本；权限通常只需 `contents: read`。若考虑版本固定与更新策略，采用现有仓库惯例。

## 最终状态

最终答复给出仓库链接、提交链接及（存在时）本次 CI 链接，清楚区分“本地已完成”“已推送”“远端检查通过”。CI 暂未结束或根本没有配置时如实说明，不编造运行结果。说明内容测试是特定性质的检查，不是全部公式的形式化证明。
