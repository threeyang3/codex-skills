# 项目收尾与知识对齐

目标是在开发或发布结束后，把“产品规格要求什么”“代码真实做了什么”“用户实际得到什么”“文档怎么说”“Agent 下一次会读到什么规则”“工作区还残留什么”对齐成一个现役答案。收尾不是多写文档，而是关闭断链、减少冲突、旧答案和不可验证状态。

默认使用用户语言。这个 Skill 会扩大检查深度，但不会扩大操作权限；删除、停服、重命名、权限变化、密钥操作或其他不可逆动作始终需要当前任务已有授权，默认只做预览和建议。

## 何时使用

适合：

- 一个功能/版本开发完成，需要同步 README、docs 和 AGENTS.md；
- 代码已经变了，但文档、规则文件或示例仍描述旧行为；
- 需要把项目交给下一次 Codex 会话或其他开发者；
- 发布后要核对 merged、deployed、live verified 与知识收尾状态；
- AI 开发留下 PLAN、TODO、debug notes、旧副本或临时脚本，需要判断哪些应保留、并入正式文档或删除；
- 用户要求“收尾”“把文档和规则同步一下”“检查 docs 和代码是否一致”。

不适合：

- 纯编码、调试或重构任务；
- 只修改一段普通文案；
- 没有项目知识上下文的泛泛“整理一下”；
- 用户只是想清理文件，而不是做知识/项目收尾。

## 完成合同

按实际项目检查以下事实面；不存在的标 `not-applicable`，无法验证的标 `pending`，不要为了完整感伪造状态。

| 事实面 | 要回答的问题 | 常见证据 |
| --- | --- | --- |
| 产品合同 | 本次真正承诺了什么，哪些 AC/限制仍有效？ | product spec、issue、决策记录、AC |
| 代码 | 当前真正实现了什么？ | 当前分支、源码、schema、配置、测试 |
| 运行态 | 用户实际得到什么？ | 本地运行、服务/API、部署标记、真实页面 |
| 文档与视觉 | README/docs/截图是否仍描述当前行为？ | README、用户指南、截图、镜头清单 |
| Agent 规则 | 下一次 Agent 收到的约束是否正确？ | AGENTS.md、项目规则、hooks、脚本 |
| 工作区 | 是否仍有未集成或未审计残留？ | git status、临时文件、旧副本、worktree |

每一面使用：`verified-current`、`changed-and-verified`、`pending`、`out-of-scope`、`not-applicable`。

不要把“git status 干净”“测试通过”“PR 已合并”中的任何一个单独当作项目已经完全收尾。

## 收尾门槛

一个用户可见功能至少应能形成这条闭环：

`产品决定/AC → 实现位置 → 验收证据 → 当前运行行为 → 用户文档/截图（若需要）`

如果其中某一段断了：

- 有实现但没有证据：补验证；
- 有规格但没有实现：标明未完成，不用文档掩盖；
- 有实现但文档仍说旧答案：更新文档；
- 有截图但当前 UI 已变化：重拍或移除旧图；
- 稳定开发规则已变化但 AGENTS.md 仍过时：更新规则；
- 无法验证：保持 `pending`，不要写成 closed。

不是每个内部重构都需要用户文档或截图；按实际受众裁剪。

## 先选轻量还是完整路径

### 轻量路径

适合个人项目、没有正式发布流程、文档较少的普通开发任务：

1. 盘点本次产品/工程目标、README、关键 Markdown、AGENTS.md/规则文件、主要入口和运行配置；
2. 核对启动命令、端口、依赖、已实现功能和当前限制；
3. 抽查本次目标/AC 是否都有实现和验证证据；
4. 修正文档与当前代码不一致的现役说法；
5. 核对关键截图是否仍对应当前 UI；
6. 核对 AGENTS.md 是否包含下一次开发真正需要的命令、边界和约定；
7. 列出会话残留和旧副本，给出去留建议；
8. 汇报已对齐、待验证和待确认删除项。

### 完整路径

出现以下任一情况时使用：

- 有 PR/CI/部署/生产环境要核对；
- 多项目或多服务联动；
- 项目规则明确规定发布/收尾流程；
- 用户要求 workspace 级审计；
- 改动影响外部接口、数据格式、迁移或运维合同。

完整路径在轻量路径基础上，再建立事实矩阵、核对远端/部署状态、搜索受影响知识面并执行更严格的验证。

## 工作流程

### 1. 发现当前规则与范围

先读取当前项目和上级作用域中真正生效的规则文件。确认：

- 本次允许修改的项目/目录；
- 是否存在项目自己的收尾、发布、文档或提交规范；
- README、docs、AGENTS.md 等各自承担什么角色；
- 是否有软链、导入或生成文件，避免修改错误的“副本”；
- 本次功能对应哪些 `D/AC`、issue、spec 或等价目标。

默认写入边界是当前项目。可以只读查看相邻项目以发现接口影响，但不要因此自动跨项目修改。

### 2. 建立现役事实矩阵

针对本次改动列出：

`事实/AC → 当前权威来源 → 实现位置 → 验收证据 → 可能过期的表面 → 应采取动作 → 如何验证`

例如：

`AC-04 损坏文件不破坏已有数据 → product spec → importer error path → regression test → README/import screenshot → 核对文案和截图 → 运行测试并实际触发错误态`

权威来源优先级由项目实际情况决定。代码和配置并不永远高于一切：协议 schema、迁移文件、产品规格或生成源也可能是更高层规格。

### 3. 核对实现与验收

读取执行阶段留下的 `AC → 实现 → 证据 → 限制` 映射；如果没有，就从当前代码和测试重建最小版本。

检查：

- Must/本次目标是否全部覆盖；
- 是否有“测试绿但没有证明产品 AC”的情况；
- 是否有产品决定在实现中被悄悄改掉；
- 是否有为了实现便利新增了未记录的限制；
- 是否有 blocker 被错误地当成已完成。

发现产品合同变化时，把变化明确记录到规格/issue/决策位置，不只写在 commit 或临时计划里。

### 4. 对齐文档与视觉

先找旧答案并就地修，不要不断追加“新版本说明”制造平行真相。

检查与本次变化有关的：

- 安装和启动命令；
- 参数、环境变量和默认值；
- API/CLI/UI 名称；
- 数据格式和兼容性；
- 架构图或模块职责；
- 示例与截图；
- 已知限制和恢复方式。

截图额外检查：

- 图片路径有效；
- 当前 UI 与截图仍一致；
- 镜头目的仍对应当前功能；
- 目标显示尺寸下仍可读；
- 截图没有泄露敏感信息或展示被移除能力。

只把已经验证或有可靠规格支撑的内容写进权威文档。无法验证的内容保留为 `pending`，不要写成确定事实。

### 5. 对齐 Agent 规则

AGENTS.md 或其他 Agent 规则只保留“下一次 Agent 不知道就容易犯错”的稳定信息，例如：

- 项目定位和关键边界；
- 如何运行与验证；
- 必须遵守的目录/文件约定；
- 不可修改的规格或安全红线；
- 项目特有的发布/交付流程。

不要把 README 全部复制到规则文件，也不要把一次性的任务进度永久写进去。已有规则文件优先最小修改，不因为收尾就重写整份。

项目有可运行代码但完全没有 Agent 规则文件时，可以建议创建最小 `AGENTS.md`；除非用户或项目习惯明确允许，不要擅自引入大量新的治理文件。

### 6. 搜索受影响知识面

围绕本次变化搜索旧字段、路由、环境变量、模型名、服务名、命令、状态词、退役符号和被替代截图。特别注意：

- 同一个旧答案是否在 README、docs、示例和规则里重复；
- 是否有旧路径仍被脚本或文档引用；
- 接口变化是否影响下游 consumer；
- 文档截图是否仍对应当前 UI；
- 旧产品决定是否仍在计划文档中被误当成现役要求。

如果发现多处重复事实，优先确定一个权威来源，其余位置缩成链接或受众专属摘要。

### 7. 清点工作区残留

常见候选包括：

- `PLAN.md`、一次性 TODO、implementation notes；
- debug 脚本和临时数据；
- `*_old.*`、`*_backup`、被替代的旧目录；
- 未使用的 worktree/分支；
- 已被正式文档吸收的中间报告。

逐项分类：

- **保留**：仍是现役规格或有独立长期价值；
- **并入**：信息有价值，但应进入 README/docs/规则；
- **删除候选**：已经完成、被替代或纯临时残留；
- **待确认**：无法安全判断。

默认只给出删除候选清单和理由。即使用户一开始说“做完顺便清理”，也不要在最终汇报之前自动删除不可逆或难恢复内容；先报告，再在获得明确授权后执行清场。

### 8. 验证

根据改动执行适用验证：

- 文档命令实际运行；
- 内部链接和图片路径有效；
- 测试/CI 与当前提交一致；
- GUI/CLI/API 名称与实际一致；
- 已发布功能在运行环境真实可见；
- AGENTS.md 中的路径、命令和规则没有死引用；
- 目标 `AC` 的关键正向/负向行为仍成立；
- 重要截图仍代表当前版本。

对发布状态使用明确阶段：`draft → PR → merged → deployed → live verified → knowledge closed → cleaned`。不要把 merged 当 deployed，也不要把 deployed 当 live verified。

## 下一次会话可恢复性

收尾时问一个简单问题：**如果下一次 Codex 会话完全没看过这次对话，它能不能只靠仓库现役文件知道怎么继续？**

至少保证：

- 运行/测试命令不依赖本次对话；
- 当前限制和未完成事项有现役位置；
- 一次性过程没有冒充永久规则；
- 关键产品决定和用户合同不只存在聊天记录里；
- 没有两个互相冲突的“当前答案”。

## 与其他 Skill 的配合

推荐产品开发链路：

`product-discovery-interview` → `agent-goal-brief` → 实现与验证 → `product-documentation` / `product-demo-visuals` → `project-closeout`

`project-closeout` 不负责重新定义产品，也不替代产品文档 Skill；它负责检查这条链从产品决定到运行态和交付物是否闭环。

## 交付说明

最终汇报应简洁覆盖：

- 哪些事实面已验证或修改；
- 哪些目标/AC 已闭环，哪些仍未闭环；
- 修改了哪些 README/docs/截图/规则；
- 哪些运行态或发布状态已经实际核对；
- 哪些事项仍 `pending`；
- 哪些文件只是删除候选，尚未动；
- 下一次会话应从哪里继续；
- 如果用户随后授权清场，再单独报告实际删除结果。
