# 产品演示截图与视觉质量控制

目标是从真实运行的软件中产出可用于 README、用户指南、发布说明和产品演示的高质量视觉素材。重点不是“截到图”，而是选择正确的场景、构图和状态，并在交付前按最终使用尺寸进行视觉验收。

默认使用用户语言。真实截图、设计稿、概念图和后期合成图必须明确区分，不得用概念图冒充已实现功能。

## 何时使用

适合：

- 为 README、产品文档、发布说明或演示材料制作截图；
- 需要展示前后对比、关键流程、复杂界面或结果状态；
- Codex 已经能截图，但需要改善场景选择、裁切、构图和质量判断；
- 需要对已有截图进行筛选、重拍建议或视觉验收。

不适合：

- 只需要证明“程序跑过”的调试截图；
- 纯设计探索、尚未实现的 UI 概念图；
- 只需要决定文档中该放哪些图，而不实际获取视觉素材；此时优先使用 `product-documentation`。

## 核心原则

1. **每张图必须有表达目的。** 先回答“这张图要让读者理解什么”，再决定截哪里。
2. **镜头目标来自文档，不重新猜叙事。** 有 `product-documentation` 的镜头清单时直接使用；没有时才补最小清单。
3. **真实状态优先。** 使用实际运行产品和可复现演示数据，不通过后期伪造产品能力。
4. **构图服务于最终阅读尺寸。** 原图很清楚但放进 README 后看不清，仍然是不合格截图。
5. **截图后必须看图。** 文件存在不等于素材合格；必须实际检查最终图片。
6. **不合格就重拍。** 不因为截图操作已经完成就降低质量标准。
7. **同组素材保持一致。** 视口、缩放、数据风格、窗口装饰和命名应协调。

## 镜头清单与捕获清单

开始前为每张目标图维护最小记录：

`shot id → 文档位置 → 表达目的/AC → route/页面 → 演示数据 → viewport → 必须出现 → 可裁掉 → 目标显示宽度 → 文件名`

如果是自动化截图，再补：

`进入状态的步骤/selector → 等待条件 → 稳定帧条件`

这份清单的作用是让截图可以重拍、复核和更新，而不是依赖“当时正好打开了这个页面”。

## 工作流程

### 1. 获取镜头目标

优先读取 `product-documentation` 产生的镜头清单。确认每个镜头：

- 要证明的功能、用户价值或 `AC`；
- 目标界面/步骤；
- 必须出现的关键元素；
- 演示数据要求；
- 使用整页、窗口、局部、序列图还是前后对比；
- 最终使用位置和大致显示尺寸。

不要按页面数量批量截图，也不要因为某个页面“看起来漂亮”就自动把它放入产品文档。

### 2. 准备可复现演示状态

在截图前把产品置于稳定且可重复的状态：

- 使用专用演示账户、fixture、seed data 或可重复脚本；
- 清除无关通知、调试日志、开发工具和随机弹窗；
- 避免私人姓名、邮箱、路径、token、真实业务数据和其他敏感信息；
- 等待网络请求、图片、字体和异步状态完成；
- 对时间、随机数、动画或实时数据造成的视觉漂移尽量固定或规避；
- 若当前 UI 本身出现错误、错位、断图或异常，不要靠裁切隐藏，先反馈给实现流程。

如果无法稳定复现，先说明限制，不要用偶然状态作为权威文档素材。

### 3. 选择合适视口、窗口装饰和缩放

根据最终用途决定画布，而不是按当前机器默认窗口：

- Web 产品优先固定浏览器 viewport，保证同组图片一致；
- 桌面产品优先固定窗口大小，避免把整个桌面作为默认画布；
- 移动端按目标设备比例或模拟器规范；
- CLI/TUI 固定终端宽高、字体和主题；
- 浏览器 chrome、地址栏、系统菜单栏只有在提供必要上下文时才保留；否则优先让产品本身成为主体；
- 避免缩放过小导致文字在 README 或文档中不可读；
- 若完整页面过长，应拆成局部图或流程序列，而非压成长图。

若关键细节在目标显示宽度下不可辨认，应改用局部截图或辅助放大图，而不是要求读者点击原图再放大。

### 4. 构图

截图不是机械记录窗口边界。优先做到：

- 主体一眼可见，关键功能占据画面主要视觉区域；
- 保留足够导航、标题或上下文，让读者知道自己在哪里；
- 去掉与表达目的无关的大面积空白、侧栏、历史记录或背景区域；
- 不把关键控件贴在裁切边缘；
- 弹窗、下拉菜单、tooltip、hover 状态只在它们本身就是重点时保留；
- 鼠标指针不要挡住文字或控件，非必要时移出主体区域；
- 同组截图中的留白、窗口比例和裁切逻辑保持一致。

“裁得越紧越专业”是错误规则；裁切应在**聚焦**与**上下文**之间取得平衡。

### 5. 捕获候选素材

同一镜头允许捕获多个候选版本，重点比较：

- 数据是否自然、足够真实；
- 关键元素是否无遮挡；
- 页面是否处于最能解释功能的状态；
- 空白是否过多；
- 滚动位置是否提供足够上下文；
- 临时 UI 是否帮助表达；
- 是否存在字体 fallback、加载残留、滚动条突兀、系统通知等视觉噪音。

对于复杂流程，优先捕获“开始 / 关键动作 / 成功结果”等少量关键节点，不记录每一次点击。

### 6. 裁切和轻量后处理

允许为提高表达质量进行非欺骗性的后处理：

- 裁掉浏览器或桌面中的无关区域；
- 统一边距和画布比例；
- 适度缩放或格式转换；
- 在明确需要时添加箭头、框选、编号或局部放大。

不得：

- 修改产品文本或数据以制造不存在的功能；
- 移除真实错误、限制或状态以掩盖产品行为；
- 将多个运行状态拼成看似一次真实操作的单张截图而不说明；
- 通过过度锐化、滤镜或装饰让截图偏离真实界面。

标注只在“没有标注就难以理解”时使用；能靠更好的裁切和构图解决的问题，不优先堆箭头和红框。

## 截图质量检查

每张候选图在进入文档前至少检查以下八项。可使用 0–2 分辅助评分：0=不合格，1=勉强可用，2=明确合格。评分用于促使复核，不代替判断。

| 检查项 | 2 分标准 |
| --- | --- |
| 表达目的 | 一眼能看出主要要说明的功能或结果 |
| 构图 | 关键内容突出，无大面积无意义空白或干扰元素 |
| 产品状态 | 数据完整，加载完成，无异常残留或调试信息 |
| 可读性 | 在最终文档显示尺寸下文字和控件仍可辨认 |
| 上下文 | 读者知道自己处在哪个页面/流程，不会因裁切失去方向 |
| 一致性 | 与同组截图的视口、缩放、数据和风格协调 |
| 真实性 | 对应真实运行结果，没有伪造已实现能力 |
| 交付完整性 | 文件命名、路径、格式、镜头 ID 和文档引用均正确 |

通常建议低于 14/16 的图片重新评估；其中“产品状态”“可读性”“真实性”任一为 0 时，不应交付。

## 最终渲染复核

实际打开最终图片，还要在**它最终出现的位置或近似宽度**再检查一次：

1. **缩略图视角**：缩小后是否仍知道主体在哪里；
2. **目标显示尺寸**：关键文字和控件是否可读；
3. **细节视角**：是否有断图、锯齿、重叠、裁切错误、光标、焦点环、滚动条或隐私信息；
4. **与相邻截图并排**：是否出现窗口尺寸、缩放、主题或数据风格跳变；
5. **与真实产品对照**：截图是否仍代表当前版本；
6. **与镜头目标对照**：这张图是否真的证明了预定功能，而不是仅仅“好看”。

如果图在原尺寸合格、实际文档尺寸不合格，视为不合格并重拍/重裁。

## 常见失败模式

看到以下情况时优先重拍，而不是修补：

- 首页看起来漂亮，但没有展示核心价值；
- 为展示一个小功能截了整屏，关键区域只占很小面积；
- 为突出细节裁得过紧，读者不知道所在位置；
- 页面尚未加载完、图片破损、字体 fallback、骨架屏未消失；
- 使用空数据或 lorem ipsum，导致产品显得不真实；
- 截图中出现终端、开发服务器通知、浏览器扩展或调试工具；
- 同组图片有的深色有的浅色、宽度不一、缩放不同；
- 依赖 tooltip 才能解释核心功能；
- 关键信息必须放大原图才能读清；
- 图片文件名和文档中的含义无法对应；
- 为了“干净”裁掉错误提示，掩盖产品真实缺陷。

## 产品类型建议

### Web

优先使用可重复的浏览器自动化进入页面、准备数据并固定 viewport。截图前等待关键 selector、字体和资源加载完成；对于动画界面，选择稳定帧。能用 route/fixture 复现的状态不要依赖人工随机点击。

### 桌面应用

优先使用应用级自动化或窗口级截图，避免把整个桌面作为默认画布。必要时隐藏其他应用和系统通知。

### CLI / TUI

如果终端本身是产品界面，固定终端宽高、字体和主题，使用短而真实的命令序列；不要让 shell prompt、绝对路径和无关历史输出淹没产品输出。

### 移动端

固定设备尺寸和系统栏状态；避免同组素材混用不同设备比例。系统权限弹窗只在文档确实需要说明时保留。

## 向文档与收尾交接

交付截图时保留：

- `shot id → 文件路径 → 表达目的/AC → viewport → 演示数据/状态 → 质量结论`；
- 未能稳定复现或未通过质量门槛的镜头；
- 截图过程中暴露出的真实产品 UI 问题。

`product-documentation` 用这些素材完成排版；`project-closeout` 检查图片路径、当前 UI 和文档引用是否仍一致。

## 与其他 Skill 的配合

- 产品尚未明确时，先使用 `product-discovery-interview`。
- `product-documentation` 负责定义文档结构和镜头清单；本 Skill 负责实际拍摄、筛选、裁切和质量验收。
- 如果截图暴露出产品本身的 UI 问题，应把问题反馈给实现流程，不要通过后期处理把缺陷藏掉。

## 交付说明

完成后说明：生成或保留了哪些视觉素材、每张图的表达目的、是否经过目标显示尺寸复核、是否存在无法稳定复现或尚未解决的产品视觉问题，以及哪些候选图被淘汰和原因。不要把“截图命令执行成功”当作“视觉素材已经合格”。
