# 产品文档策划与制作

目标是把已经实现或正在稳定实现的产品，转化为读者能够快速理解、验证并使用的文档。重点不是“把功能写下来”，而是根据读者和使用场景设计信息结构、演示顺序、截图计划和验证流程，并确保每个重要说法都能回到当前产品事实。

默认使用用户语言；必要技术名词保留英文。文档中的功能描述、截图和示例必须对应真实产品行为，不能为了文档效果虚构尚未实现的能力。

## 何时使用

适合：

- README、快速开始、用户指南、功能介绍、产品交付文档；
- 需要重新整理已有文档结构、降低理解成本；
- 需要为文档规划截图、示例、演示数据和功能顺序；
- 发布前检查文档是否与当前版本一致。

不适合：

- 单个函数注释、代码内联说明或一次性开发笔记；
- 需求尚未收敛，仍在决定产品到底做什么；此时优先使用 `product-discovery-interview`；
- 只需要获取高质量运行截图而不需要组织文档；此时使用 `product-demo-visuals`。

## 核心原则

1. **先确定读者，再确定结构。** 面向首次用户、现有用户、维护者和开发者的文档不能混成同一层次。
2. **先确认真实能力，再写文案。** 产品规格说明“想做什么”，实现证据说明“现在真的做到了什么”；用户文档必须以后者为准。
3. **先规划叙事，再截图。** 不因为“这个页面能截”就把它放进文档；每张图都要有明确作用。
4. **展示用户价值，而不是展示页面数量。** 优先解释产品解决了什么问题以及如何完成任务。
5. **文档必须可验证。** 命令、链接、截图、示例数据和功能描述都应能回到真实产品核对。
6. **避免重复维护。** 同一事实尽量有一个权威来源，通过链接引用，而不是复制到多处后逐渐失真。

## 工作流程

### 1. 识别文档类型与目标读者

根据项目和用户要求，选择需要交付的文档，不机械创建全部类别：

- **README / Overview**：帮助新读者判断产品是什么、是否适合自己、如何最快跑起来；
- **Quick Start**：最短路径完成第一个成功任务；
- **User Guide**：按真实任务流程说明功能和状态；
- **Feature Guide**：解释复杂或高价值功能；
- **Deployment / Operations**：部署、配置、升级、备份和恢复；
- **Developer Docs**：架构、扩展点、开发环境、测试和贡献方式；
- **Release Notes / Migration Guide**：说明变化、影响与迁移步骤。

如果已有文档体系，优先沿用已有结构和命名。

### 2. 建立“事实—文档”映射

在写文档前读取仓库中的 README、路由/页面、CLI help、配置、测试、示例、现有 docs，以及执行阶段留下的 `AC → 实现 → 验收证据` 映射。尽可能运行产品或检查可验证输出。

建立简短能力清单：

- 已实现且可稳定展示；
- 已实现但仍有明显限制；
- 实验性或可选；
- 尚未实现，不应写成现成功能。

对重要用户可见声明，至少知道它来自哪里：实现、运行结果、测试、schema、配置还是已验证规格。没有证据的说法先不要写成事实。

若产品规格与当前实现冲突：

- 用户文档描述当前可验证行为；
- 同时记录实现与目标规格的差异；
- 不通过文案把缺失能力“补出来”。

### 3. 设计文档叙事

用户文档通常按以下顺序组织，但应按产品实际裁剪：

1. 产品解决的问题；
2. 最核心的结果或能力；
3. 最短安装/启动路径；
4. 第一个成功用例；
5. 主要工作流；
6. 常见异常、限制和恢复方法；
7. 进阶能力；
8. 配置、参考或开发信息。

不要用内部模块划分直接充当用户文档的信息架构，除非读者本来就是开发者。

对 Quick Start 做一个额外检查：**从一个符合前置条件的新用户视角，能否只按文档完成第一个成功结果**。如果必须依赖作者脑中的隐藏步骤，文档还没完成。

### 4. 为示例和截图编写镜头清单

在实际截图前，为每个拟使用的视觉元素记录：

- `shot id`；
- 文档位置；
- 要说明的用户问题、功能或 `AC`；
- 必须呈现的 UI 状态；
- 到达该状态的稳定步骤或演示数据；
- 建议使用整页、窗口、局部还是前后对比；
- 图片中必须可读的元素；
- 可裁掉的无关区域；
- 最终大致显示宽度；
- 图片说明/alt text 要表达什么。

一张图通常只承担一个主要表达目的。若要展示多个步骤，优先使用连续小图或明确分段，而不是一张巨大的全页面截图。

需要实际生成、筛选和复核截图时，把这份清单交给 `product-demo-visuals`；后者不应重新猜“应该拍什么”。

### 5. 编写文档

写作时遵守：

- 标题描述用户任务或主题，不用模糊的“其他”“说明”；
- 首次出现的概念先定义，再使用缩写；
- 操作步骤包含必要前置条件和成功结果；
- 示例使用稳定、可复现的数据，避免敏感或个人信息；
- 对不可逆操作、权限变化、数据删除和兼容性风险做清晰提示；
- 限制和已知问题写清楚，不用营销措辞掩盖；
- 大段参数表或 API 参考与入门叙事分离；
- 截图附近的正文仍要能独立说明动作和结果，不让图片承担所有语义。

对于命令示例，尽量验证命令在当前版本可执行。对于 GUI 流程，步骤名称应与实际界面文本一致。

## 截图使用规范

文档截图必须满足以下要求：

- 展示真实运行产品；若是 mockup、设计稿或概念图，明确标注；
- 页面加载完成，没有骨架屏、断图、调试面板、无关通知或明显异常；
- 使用适合最终文档的视口和缩放；
- 关键内容在最终渲染尺寸下仍可辨认；
- 裁切聚焦主题，但保留足够上下文让读者知道自己在看什么；
- 同一文档中的截图尽量保持一致的窗口尺度和视觉风格；
- 不展示密码、token、私人路径、真实个人数据或其他敏感信息；
- 图片文件名稳定且语义化，例如 `import-success.png`，不要使用 `Screenshot 2026-...png`；
- 关键截图提供有意义的说明或 alt text，不用“截图如下”作为说明。

不要用截图代替本应可复制的文字、命令或表格。

## 文档验证

交付前执行适用检查。

### 内容一致性

- 文档描述的功能在当前版本存在；
- 重要声明能追到实现或验证证据；
- 页面名称、菜单、按钮、CLI 参数与实际一致；
- 版本要求、依赖和平台限制准确；
- 示例输出不过度承诺固定值；
- 实验性能力没有被写成稳定合同。

### 链接和资产

- 内部相对链接能解析；
- 图片路径存在，大小写与仓库一致；
- 不引用本地绝对路径；
- 外部链接只保留确有价值且稳定的来源；
- 图片文件名、镜头清单和正文引用能够对应。

### 可执行性

- Quick Start 能从符合前置条件的干净状态按步骤完成；
- 命令示例尽可能实际运行；
- 配置片段语法有效；
- 截图与对应步骤属于同一产品状态或版本；
- 文档写出的关键失败/恢复路径与真实产品一致。

### 可读性与渲染

- 新用户能在文档开头迅速判断用途；
- 核心流程不被架构细节淹没；
- 重要限制和风险不藏在末尾；
- 图片在目标渲染环境中尺寸合理；
- 截图缩到文档实际宽度后，关键文字仍能读；否则回到 `product-demo-visuals` 重拍或改用局部图。

## 向收尾阶段交接

交给 `project-closeout` 时，提供或保留这些信息：

- 新增/修改了哪些文档；
- 哪些用户可见声明有实际验证；
- 哪些截图对应哪些镜头/功能；
- 哪些内容仍因环境限制未验证；
- 是否发现产品规格、实现和文档之间仍有差异。

## 与其他 Skill 的配合

- 产品尚未定义清楚时，先使用 `product-discovery-interview`。
- 需要获取和筛选真实运行截图时，使用 `product-demo-visuals`。
- `product-documentation` 负责决定“文档需要什么图以及为什么”；`product-demo-visuals` 负责“怎样拍到合格的图”。
- 最终一致性检查交给 `project-closeout`，不要把文档阶段等同于完整项目收尾。

## 交付说明

完成后说明：新增或修改了哪些文档、面向哪些读者、哪些示例和截图经过实际验证、哪些内容因环境限制未能验证，以及是否发现文档与产品行为不一致的问题。
