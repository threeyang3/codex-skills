# Agent 目标任务书

目标是把已经基本明确的产品或工程目标，转化成一个执行 Agent 可以独立推进、可验证完成、失败时能安全停下的任务书。重点不是把实现步骤写死，而是把目标函数、边界、验收、止损和恢复机制写清楚，避免 Agent 通过“最省力但错误”的方式达标。

默认使用用户语言。这个 Skill 不替代 `product-discovery-interview`：产品方向、用户和首版范围仍不清楚时，先做需求访谈；只有当“做什么、为什么做”已经基本确定，才进入本流程。

## 何时使用

适合：

- 把一个较大开发任务交给 Codex 或其他 Agent 长时间自主执行；
- 任务跨多个文件、需要多轮验证，且用户不想持续盯着每一步；
- 需要把目标拆成可独立验收的阶段，并明确“不允许怎么完成”；
- 多 Agent 并行，需要划分写入边界和接缝；
- 探索/选型任务需要明确研究预算、证据要求和停止条件。

不适合：

- 目标用户、产品范围和验收仍然模糊；此时用 `product-discovery-interview`；
- 一个可以在当前会话快速完成的小修复；
- 用户希望边做边讨论，而不是交给 Agent 独立推进。

## 核心原则

1. **先实测，再写任务书。** 仓库里能直接验证的事实不要靠 README 或记忆猜。命令、基线、路径、测试和当前行为优先实际检查。
2. **目标与手段分离。** 用户说“加 Redis”“换框架”时，先确认真正目标；具体手段如果只是候选方案，就不要误写成不可违背的约束。
3. **验收必须防捷径。** “测试变绿”不是充分目标；同时冻结测试、阈值和验收标准，并点名禁止 skip、删测试、放宽断言、`|| true` 等假达标方式。
4. **边界优先用白名单。** 明确允许修改哪些路径、允许新增什么；其余只读。黑名单永远可能漏项。
5. **失败是允许的，失真不允许。** 无法达到目标时，可以带证据停下并说明卡点；不得为了交付“成功”而掩盖退化、绕过检查或编造结果。
6. **任务书应短而硬。** 只写执行者无法从仓库一眼得到、但会改变行为的内容。目标平台有长度限制时，以当前平台实际限制为准，不假设固定字符数。

## 工作流程

### 1. 盘点现状

先读取当前分支、项目规则、README、相关代码、测试、配置和 CI。对与目标直接相关的命令尽可能实际运行。

至少确认：

- 当前可工作的基线；
- 相关测试/检查实际命令；
- 目标涉及的权威规格文件（schema、测试、设计稿、接口合同等）；
- 哪些文件是判卷标准，不能让执行者修改；
- 是否存在文档与实际行为不一致。

碰不到执行环境时，不要编造基线；把“先验证环境与命令”写成任务 0。

### 2. 最多一轮关键提问

只问仓库中查不到、且答案会改变任务书的问题。通常不超过 5 个，优先覆盖：

- 方向取舍；
- 风险偏好；
- 验收裁量；
- 时间/成本上限；
- 是否允许并行 Agent。

每个问题尽量给出 2–4 个选项和推荐。用户没有回答但任务仍可安全推进时，允许采用默认值，但必须在任务书的“暂定决策”中明确写出，不能偷偷替用户拍板。

### 3. 判断任务类型

**执行型**：目标可以通过代码、命令、测试、产物或可观察行为判断是否完成。

**探索型**：目标本身是答案，例如选型、调查、可行性研究、找根因。

执行型以可复跑验收为核心；探索型不要用“凑够 N 条结论”当成功标准，而要强调证据质量、研究预算、尚未排除的方案和可复现性。

### 4. 写任务书

推荐按以下结构输出。项目已有目标模板时遵循项目模板，不强制另建文件。

#### A. 目标与完成态

- 为什么做；
- 做完后用户/系统会有什么可观察变化；
- 冲突时的优先级，例如“正确性 > 数据完整性 > 功能覆盖 > 速度”。

#### B. 暂定决策

列出没有经过用户明确确认、但执行必须依赖的默认值：

`问题 → 默认决定 → 为什么这样选 → 猜错的代价`

#### C. 边界

- 允许修改的路径/模块；
- 允许新增的文件类型；
- 明确只读的规格、测试、CI 或基准文件；
- 禁止顺手做的重构、依赖升级、数据迁移等；
- 涉及不可逆操作时必须停下并记录阻塞，不自行执行。

#### D. 基线与任务 0

让执行者第一步复核任务书中的关键事实：版本、测试数、性能、命令、服务状态等。

如果基线不符：

- 记录实际证据；
- 不要继续依赖错误前提；
- 做仍然不受影响的部分；
- 将需要裁决的事项写入 `BLOCKED.md` 或项目已有的阻塞记录。

长任务建议维护 `PROGRESS.md`，换会话后先读进度再继续，不从头重复。

#### E. 任务与验收

每个任务写清：

- 要达到的结果；
- 推荐从哪里开始；
- 必须遵守的约束；
- 验收命令或可观察行为；
- 如何判断失败或退化。

对“坏了可能没人发现”的检查，加入反向验证：主动制造一次可控失败，证明检查真的会红，再还原并证明恢复为绿。

#### F. 防作弊与止损

按任务需要点名禁止：

- skip/todo 测试；
- 删除或弱化断言；
- mock 掉真正需要验证的对象；
- 修改测试、阈值、基准或 CI 来迎合结果；
- 用 `|| true`、忽略退出码或吞异常制造假绿；
- 删除功能或测试以降低工作量；
- 把性能/覆盖率等指标做得比基线更差却宣称完成。

建议止损规则：同一验收连续失败 3 次后换策略或转去其他独立任务；结果明显退化时回滚该尝试并保留证据。

#### G. 完成条件

至少包含：

- 一条衡量用户真正想要结果的指标；
- 一条证明边界未被破坏的指标；
- 每个关键验收都附实际输出或可复跑证据；
- 阻塞项列表，即使为空也明确写“无”；
- 时间盒或最大尝试轮数，达到后停止并如实汇报。

## 多 Agent 并行

只有并行确实能降低总时间且用户允许时才拆分。

每个 Agent 必须有互不重叠的主要写入边界。共享文件、lockfile、schema、迁移或 CI 配置指定唯一负责人。所有子任务共享同一个全局目标和接口约定，但不得互相修改对方的验证证据。

涉及删除/清理与建设/迁移时，避免让同一个 Agent 同时负责“造”和“销毁”，除非任务本身非常小且验收独立。

## 与其他 Skill 的配合

推荐产品开发链路：

`product-discovery-interview` → `agent-goal-brief` → 实现与验证 → `product-documentation` / `product-demo-visuals` → `project-closeout`

- 产品目标仍模糊：先 `product-discovery-interview`。
- 文档与截图交付：使用 `product-documentation` 和 `product-demo-visuals`。
- 开发完成后收口代码、文档、规则和工作区：使用 `project-closeout`。

## 交付说明

最终交付一份可以直接交给执行 Agent 的 Markdown 任务书，并额外用一句话指出：哪些决定是用户已确认的，哪些仍是暂定默认，哪些事实已经实测，哪些需要执行者在任务 0 中复核。
