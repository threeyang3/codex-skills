# 作业求解、实验报告与交付

目标是让每项题目要求都能追溯到解答、实现或实际结果，并在交付前完成可行的独立核验。默认使用用户语言和自然、朴素的课程作业语气；不虚构计算、实验经历或结果。

## 适用范围与模式选择

根据任务选一个主模式，必要时组合使用：
- **理论题/数学作业**：逐题保留题目，先写分析，再写正式解答。分析可较详细，解释首次出现的重要术语、考察内容和解题思路；正式解答在步骤完整、推导正确的前提下尽量简洁，多用公式与符号。
- **编程作业**：先分析题目与现有代码接口，再实现、运行、测试并解释结果。保留题目要求的文件名、函数签名、输入输出格式和目录约定。
- **实验报告**：说明实验目标、方法、实现、实际结果及必要分析；图表必须来自真实数据，结论不得超出证据。
- **仅格式整理/打包**：用户只要求整理现有文件时，避免擅自重写内容，聚焦格式、依赖、目录和提交要求。
- 只问单个概念或求解一个简单问题时，直接回答即可；不应自动创建完整提交包。课程资料库与逐讲笔记建设优先使用 `course-materials-to-notes`。

## 阶段 1：解析题目和输入

1. 阅读完整题目、评分标准、提交说明和所有附件。若是 PDF/图片，核对公式、图表、删除线、页码与脚注；有歧义时回看原页。
2. 检查原始目录、起始代码、数据、依赖、运行入口及相对路径。不要只凭文件名推测内容。
3. 将题目拆成逐题/逐项清单：要求、所需交付物、依赖、验收方式和状态。区分明确要求与自行建议；遇到影响正确性的歧义先澄清，其他情况采用合理假设并说明。
4. 记录现有文件结构和状态，避免覆盖用户已有工作。

## 阶段 2：规划与求解

- 先明确方法、关键公式/算法和验证思路，再写最终答案或代码。
- 理论题：分析部分解释思路、概念与关键选择；正式解答给出充分但简洁的推导。题目内容应保留在交付文档中，必要时标注来源页码。
- 编程题：理解接口与约束，优先最小化修改；不因重构方便而改变外部接口。必要时说明运行环境与依赖。
- 实验题：明确变量、数据来源、实验步骤和比较基准；区分实际测量、仿真输出、理论预期与示例数据。
- 不确定的结果不能伪装成已验证事实。环境或数据缺失时，完成可完成部分并列出阻塞项。

## 阶段 3：实现与验证

按风险选择实际可执行的检查，不把静态阅读描述为程序运行成功：
- 运行题目要求的入口或最小可复现命令；记录真实退出状态和关键输出。
- 核对数值、单位、维度、边界条件、随机种子及算法更新顺序。
- 适用时使用手算、小规模测试、独立计算、基准答案或交叉实现验证结果。
- 检查图表由真实输出数据生成，轴标签、单位、图例和报告文字一致。
- 运行环境不可用时，说明未运行的原因和已完成的静态检查；不得编造运行日志。
- 修正问题后重新运行相关测试，避免只检查旧结果。

## 阶段 4：生成报告与提交包

- 报告优先以 Markdown 作为可编辑正文；用户要求 PDF 时，从核验后的正文转换，保持内容一致。根据公式和表格复杂度选择可用的排版工具。
- PDF 逐页检查公式渲染、分页、字体、表格溢出、图片清晰度和空白页。无法实际渲染/查看时说明限制。
- 提交包只包含题目要求的报告、相关源代码、运行必需的数据、依赖说明及要求的结果图。测试、缓存、虚拟环境、临时文件和过程记录默认不打包，除非用户或题目要求。
- 尽量沿用原始目录和文件名，例如 `data/`、`main/`、`plots/`；数据是运行依赖时不能当作杂项删除。
- 只有题目或提交场景需要时才创建 ZIP；创建后检查压缩包实际内容与相对路径。
- 需要署名时使用用户已提供的身份信息；用户本次明确指定的内容优先。不要把个人身份信息扩散到无关文件。

## 阶段 5：最终验收

逐项回看阶段 1 的要求清单，并确认：
1. 每道题均有对应答案，题目与解答没有错位或遗漏。
2. 公式、符号、单位、代码与结论一致；关键计算可复核。
3. 代码/实验在可用环境中运行过，或明确标记未运行项。
4. 报告中的图表、数值与实际输出一致，没有虚构结果。
5. 交付目录只包含需要的文件，必要数据与相对路径完整。
6. PDF/压缩包（若要求）已检查最终产物，而非只检查源文件。
7. 向用户说明交付位置、验证内容、运行方式及尚存限制。

## 输出风格

采用自然、朴素、准确的课程作业语气。少用套话、重复总结、自我评价和流程播报；不夸大结果。理论题按“题目—分析—正式解答”组织，实验报告按真实任务需要组织，不强行套用统一章节。用户修改内容后，重新核对受影响的报告、代码、图表和打包文件。
